01 · Positioning

What Aziiki Is

Not an accounting app, an invoicing tool, or a CRM — a single financial engine those jobs run through.

Aziiki is an AI-powered Business Operating System for entrepreneurs, freelancers, sole proprietors, and companies across Africa, built Ghana-first. The bet is simple: a business owner's record today is scattered across a notebook, WhatsApp threads, mobile money, and a bank app. Aziiki's job is to become the one place all of that lives — usable even when connectivity isn't.

The product ships in five phases. Every phase after the first exists in the codebase today, fully built, switched off by default — hide, not delete. An admin turns each one on, globally or for one account at a time, from the admin portal. Nothing here is vaporware; every feature described below is real, working code, gated by a flag that anyone with admin access can flip.

02 · Architecture Idea

The Transaction Spine

One confirmed event updates every connected record — no duplicate entry, ever.

A transaction is the shared event every other part of Aziiki derives its state from. A paid invoice isn't just a document marked "paid" — the payment updates the account balance, creates the income record, feeds cash-flow reporting, and becomes available context for the AI Advisor, all from one confirmed event.

08 · Monetization

Plans & Payments

Three tiers, self-service by default, with a manual override for the accounts that shouldn't have to pay.

Basic
The full Phase 1 core loop, free. Every new account starts here.
free
Standard
Basic, plus everything through Phase 2 — inventory, goals, debts, multi-business, signature capture, advanced brand kit.
paid
Pro
Everything — no phase ceiling.
paid

How an upgrade actually happens

  1. Admin creates a Paystack Payment Page for each paid tier and pastes the link + its exact price into /admin → Payments — no code change, no redeploy, addable whenever the link is ready.
  2. A signed-in user clicks "Upgrade" in the sidebar; Aziiki appends their email to the Payment Page URL automatically.
  3. On successful payment, Paystack calls the same webhook already used for invoice payments. It matches the charge's amount back to a tier and upgrades that account — never downgrades automatically.
  4. Every attempt is logged (matched or not) in subscription_payment_events for admin visibility.
Comping an account (family, friends, internal testing) doesn't require a payment at all — /admin → Payments → Manually set an account's plan sets any tier directly by email.

Feature-flag engine

feature_flags (key, phase, enabled_default) + user_feature_overrides (per-account exceptions). GET /api/config/features merges them into one map, computed fresh per request:

  1. Start from enabled_default for every flag.
  2. Cap by the caller's subscription tier — a flag's phase must clear the tier's ceiling (Basic → phase 1 only, Standard → ≤2, Pro → unlimited).
  3. A per-user override always wins over both, regardless of tier — the deliberate "let one account try it early" escape hatch.

New flags fail open by design: if a flag's own migration hasn't been run yet, the client treats it as its intended default rather than silently off — the alternative would hide screens for real users the moment new code ships, before the matching SQL has a chance to run.

Offline-first sync

A write that fails due to a genuine network error (not an HTTP error status) enqueues in IndexedDB instead of throwing. GETs fall back to the last cached response. A background loop replays the queue in order once connectivity returns, with a 45-second periodic safety-net retry independent of the browser's own online/offline events, and a visible banner distinguishing "syncing," "synced," and "a write had to be dropped."

Security model

  • Row Level Security everywhere — a bug in a route handler cannot leak another business's data; Postgres itself refuses the query.
  • AI prompt-injection resistance — the system prompt is a separate, higher-priority channel from user input, with explicit rules against revealing its own configuration or assisting any attack on the app or database, regardless of claimed authority in the message.
  • No secrets in the client bundle — Gemini/Paystack/Resend/Supabase-service-role keys exist only in server environment variables.
  • Login lockout + security event logging on repeated failed attempts.
  • Account deletion requires the service-role client — a user's own session token can never delete an auth.users row by itself.

11 · Process

SDLC — How This Was Built

Not waterfall, not a sprint board — a single continuous session, phased by the product teardown, verified in a real browser before every commit.

Teardown → Roadmap
A panel-review document (product, engineering, growth) scored all 22 existing features and assigned each a launch phase. That scoring is the roadmap above, not a guess.
Flag-gate, don't delete
Every feature outside Phase 1 got a migration adding it to feature_flags, then its nav entry and render path wrapped in isEnabled(key). No feature code was ever removed to hit the "smallest lovable" surface — it was switched off.
Admin portal, built last
Deliberately sequenced after the flags existed to control — a control surface with nothing to control yet is premature.
Build → verify → commit
Each batch of work was type-checked (tsc --noEmit), driven live in a browser against a throwaway test account, and only then committed with a message explaining the why, not just the diff.
Bugs caught by verifying, not assuming
Two release-blocking bugs — an admin-roles check that would have locked every admin out, and new flags defaulting to "off" before their migration ran — were both caught live against a real account before shipping, specifically because verification happened in the actual running app rather than being inferred from the code.
Migrations, handed off deliberately
Data-only changes (seeding a flag, flipping a default) were applied directly via the Supabase service-role key. Schema changes — new tables, new columns — were written as numbered SQL files and handed to the founder to run in the Supabase SQL editor, since this environment has no direct Postgres DDL access.

Known, honest gaps

No graduated rollout. Flags are global-on/off plus per-user override today — not a staged internal → beta → percentage-rollout pipeline.
Offline conflict resolution isn't a written, deliberate policy yet — the replay logic exists and works; the exact strategy for two conflicting offline edits hasn't been formally decided and documented.
No documented backup/recovery plan for financial records or critical configuration.
Feature-usage analytics are browser-local only (localStorage) — never synced server-side, so announcements can't yet target "people who use X feature most."
